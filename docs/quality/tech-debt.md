with the ideal fix noted. Update as the project progresses - do not let this
go stale.

| 2 | Router | No wildcard/method-not-allowed handling, only literal + `{param}` segments | Kept minimal for template stage per brief's "no framework" + "no over-engineering" guidance | Add a 405 response path if two methods share a pattern | Low - current route set doesn't collide |
| 3 | User management | `UserService::update()` cannot change a password; no "reset password" action exists yet | Out of scope for this pass (USR-01 only requires add/view/edit/activate-deactivate) | Add a dedicated reset-password Service method + Admin-only route if required later | Low - Admin account and demo accounts have hashes set directly in seed |

| 6 | Test database | `database/test-db-init.sql` duplicates the `CREATE TABLE` statements from `schema-and-seed.sql` by hand, instead of both being generated from one source | Needed a real `ordina_test` DB + dedicated `tester` credentials for `tests/Integration` (TEST-02) quickly; a migration-runner/shared-DDL-source setup was more machinery than this stage warrants | Extract table definitions into one PHP-readable source (array or migration files) both scripts render from, once PO/SO schema stabilizes | Medium - editing one file (e.g. adding a PO/SO column) without the other leaves integration tests running against a stale schema |
| 7 | Product images | Replacing a product's image on edit never deletes the old file from `public/uploads/products/` | Kept `ProductImageUploader` single-purpose (validate + store); cleanup is a second concern | Delete the previous `image_path` file in `ProductService::update()` once a new upload succeeds | Low - disk usage grows slowly, no correctness impact |

| 9 | Product listing performance | `MysqlProductRepository::paginateForListing()` runs the filtered/grouped query twice (once for `COUNT(*)`, once for the page of rows) rather than a single query | Avoids the deprecated `SQL_CALC_FOUND_ROWS`; two straightforward queries are easier to verify than one clever one | Revisit if the product table grows large enough for this to matter (not a concern at current/expected data volumes) | Low |
| 10 | PO goods receipt concurrency | `receiveGoods()` re-checks remaining quantity via a plain (non-locked) read before writing, inside a transaction for atomicity only - no locking | Over-receiving beyond `qty_ordered` is a soft contractual limit (also backstopped by the `chk_poi_quantities` CHECK constraint), not a stock-integrity race like SO's oversell - see `adr-0002-concurrency-safe-stock.md` | If real concurrent double-submission of the same PO turns out to matter in practice, apply the same atomic-conditional-UPDATE mechanism used for SO-01's goods issue | Low - rare edge case, and the CHECK constraint still prevents actual data corruption even if the Service-level check races |
| 11 | Purchase Order edit | No "edit items" action for a Draft PO - only create, mark-ordered, cancel, and receive | Out of scope for this pass; a wrong Draft PO can be cancelled and recreated | Add an edit action restricted to Draft status if this becomes a real workflow need | Low |
| 12 | Purchase Order create form | Validation errors don't restore the dynamic item rows the user had added (only header fields keep their values via `old`) | Item rows are built client-side via a `<template>`; repopulating N rows with per-row errors was judged more complexity than this stage warrants | Serialize submitted item rows back into the form on validation failure | Low - user re-enters items, mildly annoying but not a functional gap |
| 13 | Sales Order create form | Same gap as #12, for `/sales-orders/create` | Same `<template>`-based dynamic rows, same reasoning | Same fix, ideally shared between both forms | Low |
| 14 | Sales Order edit | No "edit items" action for a Draft SO - only create, submit, cancel | Same reasoning as #11 | Add an edit action restricted to Draft status if needed | Low |
| 15 | SO "reject" semantics | `SalesOrderService::reject()` moves `PendingApproval` straight to `Cancelled`, not back to `Draft` for revision | The brief's stated status diagram (§1.3) only shows Cancelled as the alternate branch from any pre-Fulfilled state - no "PendingApproval -> Draft" transition is described, so this was not invented | If real usage wants "send back for revision" instead of "kill the order", add a distinct transition (would need a schema change or repurposing Draft) | Low - matches the brief's literal state diagram; flagged in case the intent was actually "revise and resubmit" |
| 16 | Goods issue integration test | `SalesOrderServiceTest`'s oversell-prevention scenario runs against InMemory fakes, not yet as a `tests/Integration` test hitting real MySQL | Same time-boxing as PO-01's equivalent gap | Add a TEST-02 integration test exercising `decrementIfAvailable()`'s atomic conditional UPDATE against real MySQL before final submission | Medium - the *logic* is unit-tested, but the SQL's actual concurrency behavior under real InnoDB locking has not been verified end-to-end |
| 17 | Dashboard aggregation | `MysqlDashboardRepository` has no `InMemory` fake and no unit test - it's pure aggregation SQL (SUM/COUNT/GROUP BY), not business logic to verify without a database | Consistent with Category/Warehouse/Supplier/Customer's repositories, which also skip the fake since ARCH-01 only requires this pattern for at least one repository, not all of them | Cover with a TEST-02 integration test seeding known stock/PO/SO rows and asserting the aggregation numbers, before final submission | Medium - the queries were reviewed by hand but never executed; a typo in a `GROUP BY`/join could silently produce wrong dashboard numbers |

| 19 | Report CSV row limit | Neither CSV endpoint paginates or caps rows - a very wide date range streams every matching row in one response | Matches the brief's ask (a full export for the range, not a paginated screen) and CSV export is a one-off admin action, not a hot path | Add a sane max range or streaming safeguard if this ever runs against a much larger dataset in production | Low - not a concern at the data volumes this project targets |
